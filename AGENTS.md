# AGENTS.md

Notes for AI agents working on the `nixos-parts` repository.

## Repository overview

`nixos-parts` is a reusable dendritic `flake-parts` flake that exposes NixOS
and Home Manager modules.
It is consumed by external flakes
that import `nixosModules.biapy` / `nixosModules.default` / `homeModules.biapy`
/ `homeModules.default`.

## Layout

- `modules/nixos/default.nix` — flake-parts entry;
  defines `biapyNixOSModule` and `biapyUsersNixOSModule`
  and wires `import-tree` over `modules/nixos/_biapy`
  and `modules/nixos/_biapy_users`.
- `modules/nixos/_biapy/` — NixOS feature modules, organised by topic
  (hardware, networking, services, system, programs, security, etc.).
  Every `.nix` file in this tree is auto-imported.
- `modules/nixos/_biapy/private/` —
  internal-only NixOS options that downstream flakes are expected to set
  before the module system evaluates.
  They live under `private/` to make the public/private split explicit.
  Examples: `biapy.defaultUser`, `biapy.normalUsers`.
- `modules/nixos/_biapy_users/` —
  separate module set (`biapyUsersNixOSModule`)
  that declares user identities through `biapy.users.users`
  and the per-user GECOS `identity` submodule.
  On Linux, `isNormalUser = true; createHome = true;` are applied via
  `mkDefault` (`modules/nixos/_biapy_users/linux.nix:23`).
- `modules/home/_biapy/` — Home Manager modules, auto-imported.
  Sub-trees: `ai/` (centralized agent skills, software factory preset),
  `skills/` (third-party skill packs), `mcp/`, `programs/`, …
- `packages/` — overlay packages (sk*, batline, flyline, quien, …).
  Every `.nix` file here is auto-discovered by `pkgs-by-name-for-flake-parts`
  (`modules/flake/pkgs-by-name.nix` sets `pkgsDirectory = ../../packages`),
  and exposed as `pkgs.biapy-parts.<name>`.
- `flake.nix` — generated by `nix run .#write-flake`; do not edit manually.

## Conventions

- Files declare `lib` destructuring at the top of the `let` block,
  e.g. `inherit (lib.options) mkOption;` and `inherit (lib.types) listOf str;`.
  Match this style.
- Options that depend on other config values use a `default`
  that reads `config.…` directly, with no `defaultText`.
  Use the existing `defaultUser.nix` / `normalUsers.nix` files as a template.
- For private option defaults derived from `config.users.users`, prefer:

  ```nix
  attrNames (filterAttrs (_: u: u.isNormalUser) config.users.users)
  ```

- Hardware-per-user group assignment pattern:

  ```nix
  users.users = lib.genAttrs config.biapy.normalUsers (_: {
    extraGroups = [ "video" ];
  });
  ```

  See `modules/nixos/_biapy/hardware/backlight.nix:58`.
- Public user identity is configured through `biapy.users.users`,
  not through `users.users` directly.

## Adding a package + module

Recipe used for third-party skill packs
(e.g. `guard-skills`, `ponytail`, `mattpocock-skills`,
`stark-ai-de-agent-skills`):

1. `packages/<name>.nix` —
   a `stdenv.mkDerivation` that fetches the upstream repo
   and copies its content into `$out`.
   Use `nurl` to get the `fetchFromGitHub` args instead of hand-writing them:

   ```console
   $ nurl --fetcher fetchFromGitHub https://github.com/<owner>/<repo> v1.0.0
   fetchFromGitHub {
     owner = "<owner>";
     repo = "<repo>";
     tag = "v1.0.0";
     hash = "sha256-...";
   }
   ```

   `nurl` prints the SRI hash directly.
   `nix-prefetch-url --unpack` prints the legacy base32 nix32 form,
   which `fetchFromGitHub` rejects
   (`invalid SRI hash ... length 39 != expected length 32`)
   — convert with `nix hash convert --hash-algo sha256 --to sri <hash>`.

2. `modules/home/_biapy/skills/<name>.nix` —
   a `biapy.skills.<name>` module with `enable` plus (optionally) a `skills`
   list option typed `listOf (enum (builtins.attrNames skills))`.
   The skill name → upstream path map is a plain attrset of strings.
   The config side registers the skills into `biapy.ai.skills.skills`
   (see `modules/home/_biapy/ai/skills.nix`),
   which installs them under `~/.agents/skills`
   and propagates them to the supported agents.

3. `modules/tests/home/biapy/skills/<name>.nix` —
   a `runNixOSTest` VM test asserting the skills land in
   `~/.agents/skills/<name>/SKILL.md` and that non-selected skills are absent.

Gotchas:

- **New files must be git-tracked for the flake to see them.**
  Flakes only include git-tracked paths,
  so a brand-new `packages/*.nix` or module file is invisible until `git add`ed.
  Symptom: `nix flake show` does not list the new package,
  and `nix build .#<name>` fails with
  `does not provide attribute 'packages.x86_64-linux.<name>'`.
- **Check names with dots need quoting.**
  `biapy.skills.guard-skills` is a single attribute name, so build it as
  `nix build '.#checks.x86_64-linux."biapy.skills.guard-skills"'`.
- **`nil` runs as part of `nix flake check`** and fails on unused bindings.
  Do not inherit `mkDefault`/`mkIf` "just in case" — only inherit what is used.
- **Preset modules need their options stubbed in tests.**
  When a preset like `biapy.ai.software-factory` turns on a new submodule,
  add the matching `<name>.enable` option to the stub attrset in the preset's
  test file, otherwise the test fails to evaluate.

## Tooling

- Format: `mise run fmt` (alias `mise fmt`, also `nix fmt` via the flake).
  The formatter is `nixfmt` / `nixfmt-tree` from `github:Mic92/nixfmt-rs`
  (see `mise.toml`).
- Lint/typecheck: `nix flake check`.
- Regen `flake.nix`: `nix run .#write-flake` (alias `wf`).
- Tests live under `checks.x86_64-linux.nix-unit` and are defined inline
  as nix expressions; see `modules/nixos/default.nix`
  for an example of an inline `tests` block on a flake-parts option.
- LSP for `.nix`: `nil` (configured in `opencode.jsonc`).
- `nurl` — generate `fetchFromGitHub` / `fetchgit` / … calls with the right hash
  from a repo URL.
  Installed via `modules/home/_biapy/dev/nix.nix`.
- Local skills for repo-specific workflows live under `.agents/skills/`
  (`file-search`, `nix`, `nix-flake`).
  Skills in `~/.agents/skills/` are user-global.
- The `biapy.ai.software-factory` preset
  (`modules/home/_biapy/ai/software-factory.nix`) turns on the AI skills
  infrastructure and a set of third-party skill packs.
  Adding a skill pack to the preset means editing
  that file **and** stubbing the new option in
  `modules/tests/home/biapy/ai/software-factory.nix`.

## Gortex MCP

The repo is indexed by Gortex (`opencode.jsonc`).
The MCP server is mandatory in this environment —
prefer `mcp__gortex__*` tools for search/read/trace
and reserve host Read/Grep/Glob/Bash for cases where Gortex performance
or integration is actually bad.
Before mutating a file, call `change(operation:"impact")`;
for signature changes also `change(operation:"verify")`.
After editing, run `change(operation:"detect")`
and follow up with `tests` / `guards` / `contract` using the returned symbol
IDs.

## Pre-commit / hooks

`mise.toml` pins `prek`;
keep its hook list up to date when adding new linters or formatters.

## Writing VM tests (`pkgs.testers.runNixOSTest`)

Test files live under `modules/tests/`
and are auto-imported by `import-tree ./modules`,
so each file contributes one flake check: `checks."<module path>"`.

Layout:

- `modules/tests/home/biapy/<subdir>/<name>.nix` — Home Manager modules
- `modules/tests/nixos/biapy/<subdir>/<name>.nix` — NixOS modules

### Gotchas

- **New files must be git-tracked for the flake to see them.**
  `git add` the test file before `nix build`.
- **Relative import depth.**
  From `modules/tests/home/biapy/<a>/<b>.nix` the module under test is
  `../../../../home/_biapy/<a>/<b>.nix` (four `..` levels up to `modules/`, then
  down again).
  Same count for the NixOS tree,
  but the target is `../../../../nixos/_biapy/...`.
- **A module under test may need sibling `biapy` modules imported.**
  If module A sets `biapy.programs.foo.enable = true`,
  then `modules/home/_biapy/programs/foo.nix` must also be in the test node's
  `imports`, otherwise evaluation fails with "The option `biapy.programs` does
  not exist".
- **Home Manager configs depend on `homeModules`, not `nixosModules`.**
  A module using `stylix.targets.*` needs `inputs.stylix.homeModules.stylix` in
  `home-manager.users.testbed.imports` (plus `stylix.enable = true` and a
  `stylix.base16Scheme`).
  Do **not** import `inputs.stylix.nixosModules.stylix` in the node:
  it pulls nixpkgs overlays that collide with the NixOS module set.
- **The VM kernel command line is not built from `boot.kernelParams`.**
  Assert on the evaluated option instead,
  e.g. by writing it to `environment.etc."…".text`
  and grepping the file in `testScript`.
- **Home Manager session variables** land in
  `/etc/profiles/per-user/<user>/etc/profile.d/hm-session-vars.sh`.
  With `home-manager.useUserPackages = true` the profile directory is
  `/etc/profiles/per-user/<user>`, *not* `~/.nix-profile`.
  Variables are written as `export NAME="value"`, so grep for `NAME="value"`.
- **NixOS polkit rules** land in `/etc/polkit-1/rules.d/10-nixos.rules`.
- **Nix 2.34 rejects int interpolation.**
  `"${cfg.someInt}"` fails with "cannot coerce an integer to a string";
  use `toString`.
- **`mergeAttrsList` + `mkIf` silently drops the module config.**
  `mergeAttrsList [ { … } (mkIf false { … }) ]` merges the `if` wrapper itself,
  so the whole `config` attr is discarded when the condition is false.
  Use a plain nested attrset with `optionalAttrs` instead.
- **`statix` wants `_` for an unused argument pattern**
  and `nil` wants no unused bindings:
  use `_:` at the top of a test file
  that needs nothing from its module arguments.
- **Checks with a dot in their name need quoting:**
  `nix build '.#checks.x86_64-linux."biapy.programs.gum"'`.

  `chezmoi-dot-files/private_dot_local/bin/executable_*` and are consumed by

## Beads Workflow Integration

This project uses a Beads tracker—either the Go `bd` CLI
or the Rust `br` CLI—for issue tracking,
plus [beads_viewer](https://github.com/Dicklesworthstone/beads_viewer) (`bv`)
for graph-aware triage.
Issues are stored in `.beads/`.
`bv` auto-discovers supported JSONL exports,
including `.beads/issues.jsonl` and legacy `.beads/beads.jsonl`.

**Choose the tracker CLI from this repository's instructions and
configuration.**
Use `bd` commands in a Go Beads workspace
and `br` commands in a beads_rust workspace.
Do not run both trackers against the same workspace
or infer the tracker solely from the JSONL filename.

### Using bv as an AI sidecar

bv is a graph-aware triage engine for Beads projects.
Instead of parsing .beads/issues.jsonl / .beads/beads.jsonl directly
or hallucinating graph traversal, use robot flags for deterministic,
dependency-aware outputs with precomputed metrics
(PageRank, betweenness, critical path, cycles, HITS, eigenvector, k-core).

**Scope boundary:** bv handles *what to work on* (triage, priority, planning).
The selected tracker CLI
(`bd` or `br`) handles creating, claiming, modifying, and closing beads.

**CRITICAL: Use ONLY --robot-* flags.
Bare bv launches an interactive TUI that blocks your session.**

#### The Workflow: Start With Triage

**`bv --robot-triage` is your single entry point.**
Its `triage` object contains:

- `quick_ref`: at-a-glance counts + top 3 picks
- `recommendations`: ranked actionable items with scores, reasons, unblock info
- `quick_wins`: low-effort high-impact items
- `blockers_to_clear`: items that unblock the most downstream work
- `project_health`: status/type/priority distributions, graph metrics
- `commands`: copy-paste shell commands for next steps

```bash
bv --robot-triage        # THE MEGA-COMMAND: start here
bv --robot-next          # Minimal: just the single top pick + claim command

# TOON output (--format toon): a compact tabular encoding. Measured on this
# repository it is 7% smaller than JSON for --robot-graph but 9-15% LARGER for
# nested payloads (--robot-triage, --robot-plan, --robot-insights,
# --robot-label-health); use --stats to see both sizes before adopting it.
# TOON encoding shells out to the tru binary. With no encoder installed,
# --format toon prints a fallback warning, emits JSON with output_format "json",
# and --stats prints no sizes at all.
bv --robot-graph --format toon
bv --robot-triage --format toon --stats
```

By default, `triage.recommendations`
and `triage.quick_ref.top_picks` surface ready, actionable leaf work
(pass `--robot-include-inactive` to inspect blocked, deferred, parked,
or umbrella epic items; assigned `in_progress` items remain marked
`claimable=false`).
A suggested action records its original local ID, working directory,
and tracker route.
Use that route rather than a namespaced display ID
or an unrelated current directory.
Inspect current tracker state before execution:
analysis does not reserve work or guarantee that a later claim succeeds.

#### Other bv Commands

| Command | Returns |
|---------|---------|
| `--robot-plan` | Parallel execution tracks with unblocks lists |
| `--robot-priority` | Priority misalignment detection with confidence |
| `--robot-insights` | Full metrics: PageRank, betweenness, HITS, eigenvector, critical path, cycles, k-core |
| `--robot-alerts` | Stale issues, blocking cascades, priority mismatches |
| `--check-drift --robot-drift` | Baseline drift evaluation + live issue health alerts |
| `--robot-suggest` | Hygiene: duplicates, missing deps, label suggestions, cycle breaks |
| `--robot-diff --diff-since <ref>` | Changes since ref: new/closed/modified issues |
| `--bead-history <id>` | Single-bead lifecycle events and correlated git commits |
| `--robot-graph [--graph-format=json\|dot\|mermaid]` | Dependency graph export |

Robot analysis commands default to JSON; `--format toon` selects TOON,
and `--robot-help` defaults to text.
In JSON mode, `--graph-format=dot`
or `mermaid` puts diagram text in the `graph` field
(`bv --robot-graph --graph-format=dot | jq -r .graph`).

#### Scoping & Filtering

```bash
bv --robot-plan --label backend              # Scope to label's subgraph
bv --robot-insights --as-of HEAD~30          # Historical point-in-time
bv --recipe actionable --robot-plan          # Pre-filter: ready to work (no blockers)
bv --recipe high-impact --robot-triage       # Pre-filter: top PageRank scores
```

### Tracker Commands for Issue Management

Use exactly one command family,
matching the tracker configured for the repository.

#### Rust beads_rust (`br`)

Use `br` 0.6.0 or newer when executing saved claim commands.
It rechecks deferred status and future `defer_until` values when the claim runs,
so a recommendation captured before a deferral cannot bypass it.
This requirement applies to executing tracker claims.

```bash
br ready --json                       # Show issues ready to work (no blockers)
br list --status=open --json          # All open issues
br show <id> --json                   # Full issue details with dependencies
br create --title="..." --type=task --priority=2 --json
br update <id> --claim --json         # Claim for the current actor and start work
br close <id> --reason="Completed" --json
br close <id1> <id2> --reason="Completed" --json
br sync --flush-only                  # Export DB to JSONL after Beads mutations
```

#### Go Beads (`bd`)

```bash
bd ready --json                       # Show issues ready to work
bd show <id> --json                   # Full issue details
bd create "..." -t task -p 2 --json
bd update <id> --claim --json         # Atomically claim work
bd close <id> --json
bd dep add <issue> <depends-on>
bd export -o .beads/issues.jsonl        # Refresh the compatibility export read by bv
```

### Workflow Pattern

1. **Triage**: Run `bv --robot-triage` to find the highest-impact actionable
   work
2. **Verify**: Check the selected tracker's `show`/`ready` output
   before claiming
3. **Claim**: Use `br update <id> --claim --json`
   or `bd update <id> --claim --json`
4. **Work**: Implement the task
5. **Complete**: Use the selected tracker's `close` command
6. **Refresh for bv**: Run `br sync --flush-only`
   or the `bd export` command above so the JSONL export is current

### Key Concepts

- **Dependencies**: Issues can block other issues.
  `br ready --json` and `bd ready --json` show unblocked work.
- **Priority**: P0=critical, P1=high, P2=medium, P3=low, P4=backlog
  (use numbers 0-4, not words)
- **Types**: task, bug, feature, epic, chore, docs, question
- **Blocking**: Use `br dep add <issue> <depends-on>`
  or `bd dep add <issue> <depends-on>` to add dependencies

### Git Policy

Tracker commands do not grant permission to commit or push application code.
Follow this repository's own git and tracker instructions before staging,
committing, syncing, or pushing.
If the repository says "commit only when asked,"
that rule overrides any generic workflow advice.
